> **Language / Sprache**: [DE](#deutsche-dokumentation) | [EN](#english-documentation)

## Deutsche Dokumentation

### Das Modell in drei Dateien

Seit v0.63.0 ist `requirements.txt` eine **generierte** Datei. Bearbeitet wird sie nicht mehr —
Änderungen gehören in das maschinenlokale Overlay.

| Datei | Ort | Herkunft | Bearbeiten? |
|-------|-----|----------|-------------|
| `requirements.base.txt` | `odoodev/data/examples/vXX/` (im Paket) | Mit odoodev ausgeliefert, wird nie ins Projekt kopiert | Nein |
| `requirements.local.txt` | `vXX-dev/devXX_native/` | Maschinenlokales Overlay, von odoodev nie überschrieben | **Ja — hier eintragen** |
| `requirements.txt` | `vXX-dev/devXX_native/` | Generiert aus Baseline + Overlay | Nein — wird überschrieben |

Ein Overlay-Eintrag **ersetzt** den passenden Baseline-Eintrag an Ort und Stelle. Verglichen wird
über Paketnamen (PEP 503, normalisiert) **und** Environment-Marker — v17 pinnt sechs Pakete
zweimal unter unterschiedlichen `python_version`-Markern, deshalb reicht der Name allein nicht.

Findet sich kein exakter Treffer, wird seit 0.64.1 zusätzlich über den **Paketnamen allein**
verglichen — aber nur, wenn eine der beiden Seiten **gar keinen** Marker trägt. Ein markerloser
Eintrag gilt in jeder Umgebung und überschneidet sich damit zwangsläufig; zwei *verschiedene*
Marker gelten dagegen als komplementär und bleiben nebeneinander stehen (`< '3.13'` und
`>= '3.13'` zusammenzuführen würde eine Plattform verlieren). Ohne diesen Rückfall standen die
markerlose Baseline-Zeile `python-ldap==3.4.5` und die lokale
`python-ldap==3.4.4 ; sys_platform != 'win32'` beide in der Datei, und uv verweigerte die
Auflösung.

Ein Eintrag ohne Gegenstück in der Baseline wird in einem eigenen Block am Ende angehängt.

odoodev löst keine Abhängigkeiten auf: es bildet nur ab und schreibt die Datei — auflösen tut UV
beim Installieren.

### Befehle

```bash
# requirements.txt aus Baseline + Overlay neu erzeugen
odoodev requirements sync 18

# Alle konfigurierten Versionen auf einmal
odoodev requirements sync --all

# Nichts schreiben, nur prüfen (Exit 1, wenn veraltet) — für CI
odoodev requirements sync 18 --check

# Baseline vs. Overlay vs. installiert anzeigen
odoodev requirements diff 18
odoodev requirements diff 18 --json

# Handgepflegte requirements.txt einmalig übernehmen
odoodev requirements adopt 18
odoodev requirements adopt 18 --yes          # Baseline gewinnt bei Konflikten
odoodev requirements adopt 18 --keep-local   # lokale Pins gewinnen
```

Die Versionsangabe ist überall optional — ohne sie leitet odoodev sie aus dem aktuellen
Verzeichnis ab (`~/gitbase/vXX/...`).

### `requirements sync`

Erzeugt `requirements.txt` neu. Ist das Ergebnis identisch mit dem, was schon dort steht, wird
nichts geschrieben (`already current`).

**Schutz vor Datenverlust:** `sync` verweigert den Lauf, wenn eine `requirements.txt` existiert,
die *nicht* von odoodev erzeugt wurde und *noch kein* Overlay vorhanden ist. Sonst würde die
handgepflegte Datei durch die nackte Baseline ersetzt — jedes Paket, das nie im Bundle war, wäre
verloren. Die Existenz des Overlays gilt als Zustimmung: die Umgebung hat `adopt` hinter sich.

```
[ERROR] v18: /Users/.../requirements.txt was not generated by odoodev and no
        requirements.local.txt exists. Run 'odoodev requirements adopt' first —
        it preserves your current pins.
```

Exit-Code 1 bei blockiertem Lauf und bei `--check` mit veralteter Datei.

### `requirements diff`

Zeigt je Paket, was Baseline, Overlay und das installierte Venv sagen. Schreibt nichts. Der
installierte Stand kommt aus `uv pip freeze` im Venv der Version.

| Status | Bedeutung |
|--------|-----------|
| `local override` | Overlay ersetzt einen Baseline-Eintrag |
| `local only` | Eintrag existiert nur im Overlay |
| `not installed` | Gefordert, aber im Venv nicht vorhanden |
| `ok` | Baseline und Installation stimmen überein |

Die Tabellenausgabe blendet `ok`-Zeilen aus — sichtbar bleibt, was abweicht. `--json` liefert
**alle** Zeilen:

```json
{
  "version": "18",
  "rows": [
    {"name": "babel", "base": "2.16.0", "local": "2.17.0", "installed": "2.17.0", "status": "local override"},
    {"name": "debugpy", "base": "", "local": "1.8.5", "installed": "1.8.5", "status": "local only"}
  ]
}
```

### `requirements adopt`

Einmalige, verlustfreie Migration einer handgepflegten `requirements.txt` in das neue Modell.
Ablauf:

1. Jeder Eintrag, der von der Baseline abweicht, wird zur Auswahl gestellt
   (`keep local` / `take baseline`). Mit `--yes` / `-y` gewinnt ohne Rückfrage die **Baseline**:
   eine handgepflegte `requirements.txt` ist älter als die Baseline, ihre Version eines
   Baseline-Pakets ist also der alte Stand und keine bewusste lokale Entscheidung. Wer den
   lokalen Pin wirklich braucht, nimmt `--keep-local` — dann bleibt ausnahmslos jeder lokale
   Pin, und jeder einzelne wird als Baseline-Übersteuerung gemeldet.
2. Einträge ohne Baseline-Gegenstück und Nicht-Requirement-Zeilen (etwa `-e`- oder
   `--index-url`-Zeilen) wandern ohne Rückfrage ins Overlay.
3. Die bisherige `requirements.txt` wird als `requirements.txt.pre-adopt` gesichert, ein bereits
   vorhandenes Overlay als `requirements.local.txt.pre-adopt`.
4. Das Overlay wird geschrieben, anschließend läuft automatisch ein `sync`.

**`adopt` verweigert sich in zwei Fällen:**

- `requirements.local.txt` enthält bereits Einträge → die Umgebung hat adoptiert. Ab hier ist
  `sync` der richtige Befehl. Dieser Inhalt ist das dauerhafte Signal, nicht der Header der
  generierten Datei: ein `git pull` im gemeinsamen `vXX-dev`-Repository oder ein Kollege mit
  älterem odoodev kann den Header entfernen, das Overlay aber nicht.
- `requirements.txt` trägt den Generiert-Header und das Overlay ist leer → es gibt nichts zu
  übernehmen.

### Automatik: `init` und `start`

- **`odoodev init`** legt beim Aufsetzen ein kommentiertes, leeres Overlay an (falls keines
  existiert) und erzeugt daraus mit der Baseline die erste `requirements.txt`.
- **`odoodev start`** vergleicht vor dem Venv-Freshness-Check den im Header hinterlegten
  Baseline-Hash mit dem mitgelieferten Bundle. Weichen sie ab, wird `requirements.txt`
  zuerst neu erzeugt — die anschließende SHA256-Prüfung sieht also immer den aktuellen
  wirksamen Stand und bietet gegebenenfalls das Venv-Update an. Eine handgepflegte Datei
  fasst dieser Schritt nicht an.

### Aufbau der generierten Datei

```
# GENERATED by odoodev 0.63.0 — do not edit.
# base: v18 bundle sha256:a1b2…  local: requirements.local.txt sha256:c3d4…
# Edit requirements.local.txt instead, then: odoodev requirements sync 18

Babel==2.17.0                  # [local] neuer als die Vorgabe 2.16.0
Werkzeug==3.0.6                # muss < 3.1 bleiben (aus der Baseline übernommen)

# ── local additions ──────────────────────────────────────────
debugpy==1.8.5                 # [local]
```

Reihenfolge und Kommentarblöcke der Baseline bleiben erhalten — das macht den Git-Diff eines
Baseline-Updates lesbar, denn die Kommentare sind in diesen Dateien das eigentliche Wissen.
Jede Zeile aus dem Overlay trägt den Marker `# [local]`. Der Header führt beide Eingabe-Hashes;
den Baseline-Hash wertet `start` aus.

### Warnungen beim Zusammenführen

`sync` meldet jede Überschreibung (`overlay pins <paket><spezifikation>`) und warnt zusätzlich:

- **Overlay hält ein Baseline-Update zurück** — der lokale Pin ist älter als der der Baseline.
  Typischer Fall ist ein Pin auf Werkzeug 3.0.6 unter v16, weil Odoos `http.py` das in Werkzeug 3.1
  entfernte `werkzeug.__version__` liest — genau dieser Grund steht als Kommentar in der Baseline.
- **Overlay verliert Extras der Baseline** — der lokale Eintrag nennt weniger Extras als der
  Baseline-Eintrag, den er ersetzt.

Beides blockiert nicht, sondern wird protokolliert.

### Einsatz in CI

```bash
odoodev requirements sync --all --check
```

Schreibt nichts und endet mit Exit-Code 1, sobald eine Version veraltet ist oder der
Überschreibschutz greift.

## English Documentation

### The model in three files

Since v0.63.0 `requirements.txt` is a **generated** file. Do not edit it — changes belong in the
machine-local overlay.

| File | Location | Origin | Edit? |
|------|----------|--------|-------|
| `requirements.base.txt` | `odoodev/data/examples/vXX/` (inside the package) | Shipped with odoodev, never copied into the project | No |
| `requirements.local.txt` | `vXX-dev/devXX_native/` | Machine-local overlay, never overwritten by odoodev | **Yes — put your pins here** |
| `requirements.txt` | `vXX-dev/devXX_native/` | Generated from baseline + overlay | No — it gets overwritten |

An overlay entry **replaces** its baseline counterpart in place. The match is on package name
(PEP 503 normalised) **and** environment marker — v17 pins six packages twice under different
`python_version` markers, so the name alone is not enough.

When no exact match exists, 0.64.1 additionally compares on the **package name alone** — but only
when one of the two carries **no** marker at all. An unmarked entry applies in every environment
and therefore necessarily overlaps; two *different* markers count as complementary and stay side by
side (collapsing `< '3.13'` and `>= '3.13'` would drop a platform). Without that fallback the
baseline's unmarked `python-ldap==3.4.5` and a local `python-ldap==3.4.4 ; sys_platform != 'win32'`
were both written to the file, and uv refused to resolve.

An entry with no counterpart is appended in a dedicated block at the end.

odoodev resolves nothing: it maps and emits — UV resolves at install time.

### Commands

```bash
# Regenerate requirements.txt from baseline + overlay
odoodev requirements sync 18

# Every configured version at once
odoodev requirements sync --all

# Write nothing, just check (exit 1 when stale) — for CI
odoodev requirements sync 18 --check

# Show baseline vs. overlay vs. installed
odoodev requirements diff 18
odoodev requirements diff 18 --json

# One-time migration of a hand-maintained requirements.txt
odoodev requirements adopt 18
odoodev requirements adopt 18 --yes          # baseline wins on conflicts
odoodev requirements adopt 18 --keep-local   # local pins win
```

The version argument is optional everywhere — without it odoodev derives it from the current
directory (`~/gitbase/vXX/...`).

### `requirements sync`

Regenerates `requirements.txt`. When the result is identical to what is already there, nothing is
written (`already current`).

**Data-loss guard:** `sync` refuses to run when a `requirements.txt` exists that was *not*
generated by odoodev and *no* overlay is present yet. Otherwise the hand-maintained file would be
replaced by the bare baseline, losing every package that was never in the bundle. An overlay's
existence counts as consent — that environment has been through `adopt`.

```
[ERROR] v18: /Users/.../requirements.txt was not generated by odoodev and no
        requirements.local.txt exists. Run 'odoodev requirements adopt' first —
        it preserves your current pins.
```

Exit code 1 on a blocked run and on `--check` with a stale file.

### `requirements diff`

Shows, per package, what baseline, overlay and the installed venv say. Writes nothing. The
installed state comes from `uv pip freeze` in that version's venv.

| Status | Meaning |
|--------|---------|
| `local override` | Overlay replaces a baseline entry |
| `local only` | Entry exists only in the overlay |
| `not installed` | Required but absent from the venv |
| `ok` | Baseline and installation agree |

The table output hides `ok` rows — what remains is what deviates. `--json` returns **all** rows:

```json
{
  "version": "18",
  "rows": [
    {"name": "babel", "base": "2.16.0", "local": "2.17.0", "installed": "2.17.0", "status": "local override"},
    {"name": "debugpy", "base": "", "local": "1.8.5", "installed": "1.8.5", "status": "local only"}
  ]
}
```

### `requirements adopt`

One-time, lossless migration of a hand-maintained `requirements.txt` into the new model:

1. Every entry that deviates from the baseline is offered as a choice (`keep local` /
   `take baseline`). With `--yes` / `-y` the **baseline** wins without prompting: a
   hand-maintained `requirements.txt` predates the baseline, so its version of a baseline
   package is the older state rather than a deliberate local decision. Use `--keep-local`
   when the local pin really is deliberate — then every local pin is kept, each reported as
   overriding its baseline counterpart.
2. Entries with no baseline counterpart and non-requirement lines (such as `-e` or
   `--index-url` lines) move into the overlay without asking.
3. The previous `requirements.txt` is backed up as `requirements.txt.pre-adopt`, an already
   existing overlay as `requirements.local.txt.pre-adopt`.
4. The overlay is written, then a `sync` runs automatically.

**`adopt` refuses in two cases:**

- `requirements.local.txt` already has entries → the environment has adopted. From here on `sync`
  is the right command. That content, not the generated file's header, is the durable signal: a
  `git pull` in the shared `vXX-dev` repository, or a colleague on an older odoodev, can strip the
  header but never the overlay.
- `requirements.txt` carries the generated header and the overlay is empty → there is nothing to
  adopt.

### Automatic runs: `init` and `start`

- **`odoodev init`** seeds an annotated, empty overlay during setup (when none exists) and
  generates the first `requirements.txt` from it plus the baseline.
- **`odoodev start`** compares the baseline hash recorded in the header against the shipped bundle
  before the venv freshness check. If they differ, `requirements.txt` is regenerated first — so the
  following SHA256 check always sees the current effective file and offers the venv update when
  needed. This step never touches a hand-maintained file.

### Anatomy of the generated file

```
# GENERATED by odoodev 0.63.0 — do not edit.
# base: v18 bundle sha256:a1b2…  local: requirements.local.txt sha256:c3d4…
# Edit requirements.local.txt instead, then: odoodev requirements sync 18

Babel==2.17.0                  # [local] newer than the baseline's 2.16.0
Werkzeug==3.0.6                # must stay < 3.1 (kept from the baseline)

# ── local additions ──────────────────────────────────────────
debugpy==1.8.5                 # [local]
```

The baseline's order and comment blocks are preserved — that is what keeps the git diff of a
baseline update readable, because the comments are the actual knowledge in these files. Every line
coming from the overlay carries the `# [local]` marker. The header records both input hashes; the
baseline hash is the one `start` evaluates.

### Merge warnings

`sync` reports every override (`overlay pins <package><specifier>`) and additionally warns about:

- **Overlay holds a baseline bump back** — the local pin is older than the baseline's. Typical
  case is a pin on Werkzeug 3.0.6 for v16, because Odoo's `http.py` reads `werkzeug.__version__`,
  which Werkzeug 3.1 removed — that exact reason is a comment in the baseline.
- **Overlay drops baseline extras** — the local entry names fewer extras than the baseline entry
  it replaces.

Neither blocks the run; both are logged.

### Use in CI

```bash
odoodev requirements sync --all --check
```

Writes nothing and exits 1 as soon as one version is stale or the overwrite guard kicks in.
